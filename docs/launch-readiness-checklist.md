# Pick It Up — Definition of Done Before Real Users

**Purpose:** This is a companion document to `integration-spec.md`. The
integration spec tells Claude Code HOW to build the first real version of
the app. This document tracks WHAT must be true before that build is put
in front of real users, beyond "the code works." A good first Claude Code
build can — and should — leave most of this unchecked. That's expected,
not a failure. Treat this as the list to work through between "Claude Code
finishes the build" and "we open this up for feedback."

Items are grouped by category, each with why it matters and what "done"
looks like. Nothing here blocks Claude Code from starting — it blocks
going live.

---

## 1. Legal & Regulatory (non-negotiable — do not skip for speed)

### 1.1 Solicitor review of the coaching/intake form's scope language
- **Why:** The session intake form (`PickItUp_SessionIntakeForm_v1.md`)
  needs its scope wording checked by a solicitor before it's used with
  real clients — this was already flagged as a non-negotiable pre-launch
  item.
- **Done when:** A solicitor has reviewed and signed off on the intake
  form's language, specifically the boundary between counselling/coaching
  and anything that could read as clinical/diagnostic.

### 1.2 Professional indemnity insurance for digital coaching delivery
- **Why:** Already flagged as a non-negotiable pre-launch item — 1-on-1
  Zoom coaching needs to be covered.
- **Done when:** A policy is in place that explicitly covers remote/digital
  coaching delivery, not just in-person practice.

### 1.3 AUSactive registration
- **Why:** Already flagged as a pre-launch priority — this sits within the
  SIS40221 (fitness coaching) scope of the app's movement programming.
- **Done when:** Registration is complete and current.

### 1.4 Privacy Policy + APP-compliant consent flow
- **Why:** Health and mood data is "sensitive information" under the
  Privacy Act 1988 — this needs express consent, not a buried checkbox.
- **Done when:** A real Privacy Policy exists (not placeholder text),
  consent is explicitly captured at signup, and APP 11 security
  obligations (reasonable steps to protect the data) are met by whatever
  backend Claude Code builds.

### 1.5 APP 1 automated-decision-disclosure readiness
- **Why:** This obligation becomes active 10 December 2026. The app makes
  automated recommendations (recipe scoring, program generation) that this
  rule will cover.
- **Done when:** The app discloses, in plain language, that recommendations
  are automated — doesn't need to be live today, but the disclosure copy
  and the mechanism to show it should exist before December 2026.

### 1.6 Scope-of-practice language audit (ongoing, not one-time)
- **Why:** The TGA's wellness-software exclusion only holds if no function
  makes diagnosis/treatment claims about a disease or condition. This is a
  narrow line, and it's easy to cross accidentally in copy, not just in
  features.
- **Done when:** Every place the app or its AI-generated content could
  plausibly use a diagnostic word ("depression," "anxiety," "eating
  disorder," "screen for," "treat") has been checked and stays clear of
  that language. This isn't a single sign-off — re-check this whenever new
  AI prompts or copy are added.

## 2. Data & Content Quality

### 2.1 Trainer review of the exercise schema's derived fields
- **Why:** `pattern`, `difficulty`, `coordination_demand`,
  `confidence_demand`, `energy_demand`, and `nervous_system_effect` in
  `program-engine-data.js` were generated by heuristic from the existing
  exercise tags — not reviewed by a trainer. The file's own header comment
  flags this. A wrong label here isn't cosmetic; it's the data the
  contraindication and program-generation logic relies on.
- **Done when:** Josh (or another qualified trainer) has gone through all
  37 entries in `EXERCISES` and corrected any fields that don't hold up —
  the "Superman" → "Full Body" pattern mislabel mentioned in the code
  comments is a known example to start with.

### 2.2 Nutrition data verification against AUSNUT/FSANZ
- **Why:** Every recipe in `recipe-engine-data.js` is flagged
  `nutritionSource: "estimated"`. For a counselling-led health product,
  shipping unverified macro/calorie claims as if they were precise is a
  credibility and accuracy risk.
- **Done when:** Either (a) ingredient macro values have been checked
  against AUSNUT/FSANZ, or (b) the `nutritionSource: "estimated"` flag is
  still honestly surfaced in the UI everywhere nutrition data is shown —
  don't let this disclosure quietly disappear during the Claude Code
  rebuild.

### 2.3 Shopping list / ingredient-quantity data
- **Why:** `buildShoppingList()` works from free-text ingredient patterns,
  not real per-recipe quantities — it's a best-effort estimate, flagged as
  such in the code.
- **Done when:** Either a real `recipe_ingredients` join table with actual
  quantities exists, or the "quantities are estimated" disclosure stays
  visible in the UI. Not required for a first build, but shouldn't be
  silently presented as exact once it's a real product people shop from.

### 2.4 Christian lens scripture content review
- **Why:** The pillar-to-scripture mapping was written to be broadly
  Catholic/Protestant-acceptable, but wasn't reviewed by anyone with
  theological background.
- **Done when:** Someone with relevant background has sanity-checked the
  four scripture references and the pillar-framing language before this
  feature is presented as a real, considered offering rather than a
  first draft.

## 3. Technical / Infrastructure (not covered by the integration spec)

### 3.1 Real backend and database
- **Why:** Everything built so far runs as client-side state in a single
  React file. There is no persistence, no auth, no real data storage.
  The integration spec covers how the engines and main app's logic fit
  together — it does not design the backend.
- **Done when:** Claude Code has stood up a real database (the spec
  suggests Postgres/Supabase as an example, not a requirement) and basic
  auth, and user data survives a page refresh / new device.

### 3.2 Automated test coverage
- **Why:** Validation so far has been brace/paren balance checks and
  manual functional tests run during development — appropriate for a
  single-file prototype, not sufficient once this is a real multi-file
  app with a backend.
- **Done when:** Core logic (contraindication checking, scoring functions,
  TDEE/macro calculations) has actual unit tests, and there's at least a
  basic smoke test for the main user flows (check-in → session, goal →
  recipe recommendation).

### 3.3 Exercise data consolidation decision
- **Why:** `MDB` (live app) and `EXERCISES` (program engine) are
  duplicate data by design, kept separate deliberately until 3.1 above
  (trainer review) is done. Leaving this duplicated forever is its own
  form of technical debt.
- **Done when:** Once trainer review (2.1) is complete, make an explicit
  decision to retire `MDB` in favour of `EXERCISES` as the single source
  of truth, and update Movement/Player to read from it. Don't let this
  linger past the point where it's safe to consolidate.

### 3.4 `getSession` vs `generateProgram` decision
- **Why:** The live app still has both the original LLM-based session
  generator (soft injury handling) and the new deterministic one (hard
  contraindication warning) running side by side, by design, so they can
  be compared with real usage first.
- **Done when:** After real user feedback on both, make an explicit call
  on whether `generateProgram` replaces `getSession` outright, or whether
  both stay as a permanent "quick" vs "detailed" choice. Don't let this
  sit unresolved indefinitely — the deterministic version is the
  safer pattern per the market research, so the default lean should be
  toward replacing the weaker one once confidence is earned.

## 4. Honest Disclosures to Keep Visible (don't let these get "cleaned up" away)

These are small, deliberate pieces of UI copy that exist because they're
the honest thing to show, not because they look polished. Each one was
added for a specific reason — flag this list to Claude Code explicitly so
none of them get stripped out during a redesign pass for the sake of
visual tidiness:

- "Not medical advice" disclaimer on the Detailed Session / program
  generator results.
- `nutritionSource: "estimated"` disclosure on recipe nutrition info.
- Shopping list "quantities are estimated, not exact" note.
- The one-tap contraindication warning interstitial — must stay mandatory
  and block progression, not become a passive banner.
- BMI muscle-mass caveat and WHtR explanation copy.

## How to use this document

Hand this to Claude Code alongside `integration-spec.md`. The integration
spec is the build instructions; this is the readiness gate. A reasonable
sequence:

1. Claude Code builds the first real multi-file app per the integration
   spec (Section 3.1–3.4 above will mostly get addressed naturally as
   part of that work — backend, tests, data consolidation).
2. Before inviting real users, work through Sections 1 and 2 above —
   these need Josh's time and possibly a solicitor's, not just more code.
3. Section 4 is a standing check — re-confirm it hasn't quietly regressed
   any time there's a UI redesign pass.
